# 실험 6: 커널 지연시간과 core mesh shape

## 측정 범위

[run.py](run.py)는 bfloat16 단일 커널을 8×8 CCG 장치의 좌상단에서 잘라낸 12가지 core mesh shape에 각각 수동 배치한다. 각 구성은 새 장치에서 독립적으로 실행한다. 아래 수치는 [kernel_latency.csv](.cache/kernel_latency.csv)의 `latency_cycles`이며, 실행된 커널의 `completion_cycle - start_cycle`이다. 따라서 컴파일 시간이나 전체 애플리케이션 응답시간이 아닌 **커널 실행 구간의 시뮬레이션 사이클**이다. 그래프의 speedup은 `1x1 latency / 해당 mesh latency`로 계산한다.

장치 설정은 코어당 1MB 로컬 캐시, 128KB LD 버퍼, 128KB ST 버퍼 및 1GHz 클록을 사용한다. 입력·출력 중간 텐서는 로컬 캐시를 우선하며, weight는 장치 메모리를 우선한다. 로컬 캐시 배치에 실패하면 장치 메모리로 배치된다. 각 구성에서 사용 가능한 DMA 타일은 동일하게 16개이며, 바뀌는 주요 변수는 커널에 할당한 코어의 **개수와 2차원 모양**이다.

## 커널별 분석

### Linear: 출력 타일 수가 빠르게 병렬성의 상한이 된다

세 workload는 각각 `M=32`, `N=K=1024/512/256`인 행렬곱과 bias 덧셈이다. 32×32 출력 타일을 사용하므로 출력 타일은 large 32개, medium 16개, small 8개뿐이다. 시뮬레이터는 출력 타일을 코어에 배정하고, 각 타일에서 입력·weight의 K축 타일들을 읽어 계산한다. weight는 장치 메모리에 배치되므로 코어 수가 늘 때 weight 읽기와 데이터 이동 비용도 영향을 준다.

- Large는 1×1에서 4×8로 4.36배 빨라지지만 4×8과 8×8의 지연시간은 모두 4,441 cycles이다. 출력 타일 32개에 이미 32개 코어를 사용할 수 있어, 64개 코어로 늘려도 추가 병렬 작업이 생기지 않는다.
- Medium은 4×4가 1,597 cycles로 최저이고 8×8은 1,884 cycles로 오히려 느리다. Small도 2×4가 791 cycles로 최저이고 8×8은 934 cycles다. 출력 타일이 16개·8개인 상황에서 코어를 더 늘려도 작업량은 그대로인 반면, 배치 모양과 메모리 접근 경로는 달라진다.
- 같은 8개 코어라도 가로로 긴 1×8이 세 크기 모두에서 8×1보다 빠르다. 이는 출력 타일 매핑, weight 재사용, 메모리와 코어 간 위치가 **mesh의 가로·세로 방향에 민감하다**는 관찰이다. 어떤 비용이 몇 사이클을 차지하는지는 현재 CSV만으로 분리할 수 없다.

### Conv2d: 큰 문제일수록 코어 확장의 이익이 크다

입력은 NHWC, weight는 HWKC이며 모두 3×3 필터, stride 1, padding 1이다. 출력 타일 형태가 `(1, 1, 32, 32)`이므로 높이 방향 위치와 batch·출력 채널별로 독립 출력 타일이 생기며, 폭 방향 32개 원소는 한 타일에 묶인다. 출력 타일 수는 large 4,096개, medium 1,024개, small 256개다. 각 출력 타일은 대응되는 입력 영역과 여러 weight 타일을 참조한다.

- Large는 1×1의 1,267,718 cycles에서 8×8의 55,571 cycles로 감소해 22.81배 빨라진다. Medium은 75,598에서 8,299 cycles로 9.11배다. 독립 타일이 많아 계산을 여러 코어로 나누는 효과가 크다.
- Small은 2×8에서 2,849 cycles로 최저이고 8×8에서는 4,167 cycles다. 입력 8×8, 출력 채널 32의 작은 연산은 코어를 더 투입할 때 줄어드는 코어당 계산량보다 타일 분산·메모리 전송·동기화 비용의 영향이 커진 것으로 해석된다.
- 같은 32개 코어의 4×8과 8×4도 다르다. Large는 각각 77,283과 84,928 cycles다. 타일 위치, 데이터 소유 코어와의 거리, 메모리 경로가 모양에 따라 달라지는 것으로 볼 수 있다. 현재 결과만으로 네트워크 혼잡과 원격 읽기의 기여분을 정량화할 수는 없다.

### Elementwise/ReLU: 캐시 적재 가능 여부와 배치 정렬이 지배적이다

ReLU는 원소당 연산량이 작다. 출력 타일은 large 1,024개, medium 256개, small 64개지만, 계산보다 입력 읽기·출력 쓰기 경로가 더 크게 작용할 수 있다. 이 실험의 중간 텐서는 로컬 캐시를 우선하며, 캐시 용량이 모자라면 장치 메모리로 넘어간다.

- Large의 입력과 출력은 각각 약 2MB다. 1×1에서는 로컬 캐시 1MB에 모두 놓을 수 없지만, 1×8에서는 코어별로 나뉘어 들어갈 수 있다. 실제로 지연시간은 32,894에서 76 cycles로 급감한다. 이 **432.82배**는 8개 코어의 산술 처리량만으로 가능한 배속이 아니며, 메모리 배치 경로가 바뀌는 효과가 지배적임을 시사한다.
- Medium도 입력·출력이 각각 약 512KB다. 1×1에는 LD/ST 버퍼 예약분까지 고려하면 두 텐서를 모두 로컬 캐시에 넣기 어렵고, 1×8에서는 4,453에서 23 cycles로 떨어진다. Small은 총 입력·출력 데이터가 약 256KB라 1×1도 41 cycles로 빠르며, 8×8에서 6 cycles까지 내려간다.
- Large의 1×8은 76 cycles인데 2×8은 1,139 cycles, medium의 1×8은 23 cycles인데 2×8은 344 cycles다. 텐서 타일은 사용 가능한 코어에 순환 배치되고, 출력 타일의 계산 코어는 별도 2차원 매핑으로 정해진다. 1×8에서는 두 순서가 잘 맞을 수 있지만 행을 늘리면 많은 타일이 계산 코어와 다른 코어에 놓여 원격 전송이 발생할 수 있다. 이 결과는 **매핑·배치 불일치가 유력한 설명**이지만, 원격 전송량을 기록한 별도 로그 없이 그 비용을 확정할 수는 없다.

### Reduction/Sum: 작은 문제는 1×1의 데이터 지역성이 유리하다

각 workload는 `M×N` 텐서의 마지막 축을 합산한다. 출력 타일 수는 large 32개, medium 16개, small 8개이며, 출력 타일 하나가 해당 행 블록의 입력 축 타일 여러 개를 모아 읽는다.

- Large는 1×1에서 17,060 cycles이지만 8×8에서 1,703 cycles로 10.02배 개선된다. 2MB 입력을 한 코어의 로컬 캐시에 모두 두기 어렵고 출력 타일도 32개라, 여러 코어의 캐시 용량과 계산 병렬성이 도움이 된다.
- Medium과 small은 각각 **1×1에서 76, 23 cycles로 최저**다. 입력은 각각 약 512KB, 128KB여서 1개 코어의 로컬 캐시에 넣을 수 있다. 한 코어에서 합산하면 여러 입력 타일을 같은 코어에서 읽을 수 있고 코어 간 전송도 피한다.
- 반대로 medium의 1×4는 1,702 cycles, small의 1×4는 505 cycles로 1×1보다 약 22배 느리다. 입력 타일을 여러 코어의 캐시에 순환 배치한 뒤 출력 타일별 합산을 다른 코어에 맡기면 원격 읽기가 많아질 수 있다. 8×8에서도 medium 620 cycles, small 211 cycles로 1×1보다 느리다. 여기서 작은 mesh의 우위는 코어가 계산을 더 빨리해서가 아니라 **이미 충분히 작은 데이터를 한 곳에 두는 이점**으로 설명된다.

## 왜 코어 수에 비례해 지연시간이 줄지 않는가

커널 시간은 단순히 `총 연산량 / 코어 수`가 아니다. 이 시뮬레이터는 출력 타일을 코어에 배정한 뒤 타일별 입력 로드, 계산, 출력 저장 stage를 실행한다. 로컬 캐시 적재 여부, 장치 메모리 접근, 원격 코어 읽기, LD/ST 버퍼 제약, stage 동기화가 모두 경로에 들어간다. 따라서 다음과 같은 상한과 역효과가 생긴다.

1. **독립 작업 수의 상한:** linear는 출력 타일이 8~32개뿐이다. 코어 64개를 줘도 추가로 나눌 출력 타일이 없다.
2. **고정 비용과 데이터 이동:** 작은 conv2d·reduction은 코어당 계산량이 작아질수록 로드·저장·동기화 비용의 비중이 커진다.
3. **메모리 계층의 불연속성:** ReLU는 코어 수 증가로 로컬 캐시 배치가 가능해지는 지점에서 지연시간이 계단식으로 급감한다. 반대로 여러 코어로 분산하면서 로컬 데이터가 원격 데이터로 바뀌면 지연시간이 늘 수 있다.
4. **2차원 배치와 자원 경쟁:** 같은 코어 수라도 가로·세로 shape에 따라 출력 타일 소유 코어와 입력 타일 보관 코어가 달라진다. 통신 거리, 전송 경로, 메모리 요청 경쟁도 달라진다.

특히 1×8 ReLU의 극단적인 speedup이나 1×1 reduction의 우위는 **이 시뮬레이터의 텐서 배치·매핑 정책을 포함한 결과**다. 이를 코어 개수만의 성능 법칙으로 일반화하면 안 된다. 원인별 기여를 확정하려면 구성별 텐서의 LOCAL_CACHE/DEVICE_MEMORY 배치, 코어 간 전송량, DMA 바이트, 코어별 stage 수와 유휴 시간을 함께 기록해야 한다.
